# Team Memory — подтверждённые знания наставника (MVP)

## Цель

AI-buddy не придумывает ответы на отсутствующие в документации вопросы. Стажёр
может обратиться к наставнику; наставник отвечает и **отдельно подтверждает**,
что его ответ можно использовать как повторно применимую инструкцию. Следующие
стажёры получают проверенный ответ без повторного обращения к человеку.

В деморежиме продукт рассчитан на одного тестового стажёра `user_id=1`.
Публикация означает, что информация станет доступна любому посетителю демо.
**Не публикуйте пароли, токены, персональные данные и реальные внутренние
инструкции компании**. Настоящей авторизации/изоляции команд здесь нет.

## Как использовать

1. В роли стажёра открой «Вопросы наставнику» и отправь вопрос.
2. Открой «Кабинет наставника», ответь на вопрос.
3. После ответа нажми **«✦ Добавить в Team Memory»** возле обращения.
4. Убедись, что подтверждённый ответ появился в блоке **Team Memory**.
5. Снова спроси AI-buddy то же самое (или очень похоже сформулированный вопрос).
   Ответ берётся из подтверждённой записи и имеет источник `Team Memory #N`.
6. Нажми «Отозвать», чтобы информация перестала использоваться. При изменении
   старого ответа наставника требуется новое одобрение, иначе он скрывается.

## Как это устроено технически

- Новая таблица SQLite `knowledge_entries` хранит оригинальные вопрос,
  подтверждённый ответ, ID обращения и время одобрения.
- Роуты `GET /team-memory/entries`, `POST /team-memory/publish` (JSON
  `{ "question_id": 1 }`) и `DELETE /team-memory/entries/<id>`.
- Записи извлекаются из SQLite **только после явного одобрения наставником**.
- Простая консервативная лексическая проверка совпадения позволяет находить
  совпадающие вопросы без внешнего API и без повторной индексации FAISS.
- Если найден подтверждённый ответ, сервер возвращает **буквально проверенный
  текст наставника**, а не перегенерирует его нейросетью. Ответ помечается
  `answer_origin: mentor_verified`. Таким образом исключается искажение
  подтверждённой инструкции моделью.
- При отсутствии подходящего ответа выполняется обычная логика AI:
  существующий `demo_chat` или `rag.py` Антона (в `unified_app.py`).
- Вызов оригинального `rag.py` и его FAISS-индекс не изменяется. Это гибридная
  схема поиска: динамическая Team Memory перед основным RAG. **Это не обучение
  весов модели и не добавление в индекс FAISS.** Для промышленной версии
  полезно сделать векторный поиск одобренных Q&A и командную изоляцию.

## API, проверки и ограничения

`POST /team-memory/publish` проверяет, что обращение существует, принадлежит
тестовому пользователю и имеет непустой ответ. Нельзя опубликовать неотвеченный
вопрос. Публикация повторно возможна после изменения текста ответа, но требует
нового явного клика. Старые одобрения перестают действовать **сразу после
изменения** наставником текста ответа или вопроса (проверка через JOIN).

Старые таблицы `tasks` и `mentor_questions` не меняются. Файл БД и Docker volume
сохраняются. `init_team_memory_db()` создаёт новую таблицу идемпотентно.

### Важно до реального развёртывания

Нужно добавить авторизацию, права наставника на публикацию и отзыв, разделение
по командам и владельцам знаний, аудит, модерирование и защиту конфиденциальной
информации. Пока это только демонстрационный сценарий.

## Проверка

```bash
npm run test:coverage
python -m pytest -v

docker compose -f compose.yaml -f compose.unified.yaml up --build
```

Для проверки реального RAG нужны настроенные ключи Yandex Cloud. В демонстрационном
режиме Team Memory работает **без ключей**, но не использует языковую модель.
